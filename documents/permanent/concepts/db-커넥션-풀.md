# DB 커넥션 풀(Database Connection Pool)

## 정의

DB 커넥션을 미리 생성해 두고 필요 시 빌려 쓰고 반납하는 패턴; 커넥션 생성 비용(TCP 핸드셰이크·SSL/TLS 협상·계정 인증·백엔드 프로세스 할당)을 초기 1회로 상각해 요청당 오버헤드를 제거한다.

## 맥락

PostgreSQL은 커넥션당 별도 [[프로세스]]를 생성하므로 커넥션 수가 늘수록 메모리 소비와 [[컨텍스트-스위칭]] 비용이 증가한다. 이 때문에 풀 사이즈는 "많을수록 좋다"가 아니라 CPU가 실제로 처리할 수 있는 양에 맞춰야 한다.

**주 사이징 공식 (PostgreSQL 위키 + HikariCP 위키)**:
```
최대 풀 사이즈 = (물리 CPU 코어 수 × 2) + 유효 스핀들 수
```
- × 2인 이유: 쿼리는 CPU 작업 ↔ I/O 대기를 반복하고, I/O 대기 동안 코어가 유휴 상태가 되어 커넥션 1개를 추가로 끼워 넣으면 CPU 활용률 ~100% 달성.
- 2026년 NVMe SSD 환경에서 스핀들 = 0이므로 실질 공식은 **물리 코어 수 × 2**.
- 하이퍼스레딩(논리 코어)은 제외한다 — DB 작업처럼 캐시 미스가 많은 작업에서 HT 효과가 미미하고 오히려 캐시 경쟁 유발.

**실무 사이즈 패턴**:
- 소규모: 10 / 중소규모: 10~30 / 트래픽 많은 서비스: 30~50 (부하 테스트 검증 후)
- **100개 이상은 안티패턴**

**다중 WAS 환경 분배**:
```
각 WAS 풀 사이즈 = (DB 코어 × 2) ÷ WAS 인스턴스 수
```
전체 WAS 풀 합산 ≤ DB 맥스 커넥션 × 0.8 (안전 마진). WAS 수가 동적으로 변하는 오토스케일링 환경에서는 PgBouncer 같은 외부 풀러 도입을 권장한다.

**기존 시스템 적용 판단 기준**: 활성 커넥션 / 맥스 풀 사이즈 < 25%면 축소 안전, 65% 이상이면 줄이지 말 것.

**주요 함정**: 롱 트랜잭션(가장 흔한 고갈 원인), 타임아웃 미스매치(`maxLifetime` > DB idle timeout), Cm > 1 중첩 트랜잭션, 커넥션 누수.
