# DB 커넥션 풀 사이징 기본과 함정 (아키텍트 관점)

## 요약

DB 커넥션 풀 사이즈를 크게 잡을수록 처리량이 오히려 줄어드는 역설을 다루는 강의로, PostgreSQL 위키·HikariCP 공식 문서 출처의 '물리 코어 × 2 + 스핀들 수' 공식과 리틀의 법칙 진단법을 중심으로 풀 사이징 원칙, 다중 WAS 환경 분배, 실무 함정 4가지를 구체적으로 설명한다. 신규 시스템 초기값 설정과 트러블슈팅 진단 기준으로 실무 즉시 적용 가능하다.

## 핵심 내용

### 커넥션 풀 개요와 생성 비용

[[db-커넥션-풀]]은 DB 커넥션을 미리 생성해 두고 필요 시 빌려 쓰고 반납하는 패턴이다. 개념 상세는 [[db-커넥션-풀]] 참조. 커넥션 생성에는 TCP 핸드셰이크·SSL/TLS 협상·DB 계정 인증·백엔드 프로세스 할당(PostgreSQL은 커넥션당 별도 [[프로세스]] 생성 → 메모리 증가)이 포함되어 수 ms~수십 ms 오버헤드가 발생한다. 풀을 쓰면 초기 1회 생성 후 재사용하므로 오버헤드가 누적되지 않는다.

### 언어별 기본 풀 사이즈

| 언어/라이브러리 | 기본 최대 풀 사이즈 |
|---|---|
| Java (HikariCP, Spring Boot 2.0+) | **10** |
| .NET (ADO.NET 내장 풀) | **100** |
| Node.js (node-postgres pg pool) | **10** |
| Python (SQLAlchemy QueuePool) | **5** (overflow 10, 최대 15) |

.NET의 100개는 MS SQL Server의 맥스 커넥션이 충분히 크기 때문이며, Microsoft 공식 가이드는 "기본값 그대로 쓰지 말고 워크로드에 맞게 조정하라"고 명시한다. .NET을 제외한 라이브러리들이 5~15 범위에 수렴하는 것은 기술적 근거가 있음을 시사한다.

### 핵심 역설: 커넥션 수가 많을수록 느려진다

Oracle RWP(Real-World Performance) 문서는 "연결 수를 줄이면 CPU 부하가 줄어들어 응답 속도가 빨라지고 처리량이 증가한다"고 밝힌다. HikariCP 위키 벤치마크에서도 PostgreSQL 기준 약 50 커넥션 부근부터 TPS가 평탄화됨을 확인할 수 있다.

느려지는 이유는 [[컨텍스트-스위칭]] 비용, 락 경쟁 증가, 캐시 효율 저하 세 가지로 요약된다. 이는 USL(Universal Scalability Law)로 설명되며, [[컨텍스트-스위칭]] 상세는 해당 개념 참조. 핵심 원리는 "동시에 일하는 커넥션은 CPU가 처리할 수 있는 양만큼만 의미가 있다"이며, 이는 [[쓰레드]] 풀·HTTP 클라이언트 풀 등 모든 풀에 동일하게 적용된다.

### 풀 사이즈 산정 공식

**주 공식 (PostgreSQL 위키 + HikariCP 위키)**:

```
최대 풀 사이즈 = (물리 CPU 코어 수 × 2) + 유효 스핀들 수
```

엄밀히는 활성 커넥션 수에 대한 공식이나, 실무에서는 최대 풀 사이즈 가이드로 활용한다. HikariCP 공식 가이드는 "다른 DB에도 대체로 적용 가능"하다고 명시한다.

- **× 2인 이유**: DB 쿼리는 CPU 작업 ↔ I/O 대기를 반복하고, I/O 대기 동안 코어가 유휴 상태가 되어 다른 커넥션 1개를 끼워 넣으면 CPU 활용률 ~100% 달성. × 3, × 4는 [[컨텍스트-스위칭]]·캐시 무효화·락 경쟁 비용으로 오히려 역효과.
- **하이퍼스레딩 제외 이유**: 논리 코어는 진짜 연산 자원이 아니고, DB 작업처럼 메모리 접근 빈번·캐시 미스 많은 작업에서 HT 효과가 미미하며 두 HT [[쓰레드]]가 같은 캐시를 경쟁해 성능 저하 가능. 예: 8코어 16스레드 CPU → 공식에는 8 대입.
- **스핀들 수**: HDD 시대 개념(물리 디스크 회전축 수). 2026년 현재 NVMe SSD 환경에서는 스핀들 = 0이므로 **실질 공식은 물리 코어 수 × 2**.

**보조 공식 — 데드락 회피 최소 커넥션 수 (HikariCP)**:

```
최소 커넥션 수 = Tn × (Cm - 1) + 1
(Tn: 동시 스레드 수, Cm: 한 스레드가 동시에 점유하는 최대 커넥션 수)
```

중첩 트랜잭션 등 Cm > 1인 코드에서 데드락 방지용이며, 일반 앱은 Cm = 1이라 결과값 = 1로 의미 없다. **풀 사이즈 설정 공식이 아니라 데드락 발생 시 진단 도구**로 활용한다.

### 리틀의 법칙으로 진단하기

[[리틀의-법칙]]은 풀 크기를 정해 주는 공식이 아니라 **풀 부족 vs 쿼리 성능 부족을 구별하는 진단 도구**다. 개념 상세는 [[리틀의-법칙]] 참조.

```
TPS = 활성 커넥션 수 ÷ 쿼리 실행 시간(초)
```

예시: 풀 사이즈 16, 평균 활성 커넥션 14, 쿼리 실행 시간 50ms → 이론 TPS = 14 ÷ 0.05 = 280. 활성 커넥션이 맥스의 ~90%에 도달하면 처리량 증가 방법을 검토해야 한다.

**처방 순서**: ① DB 코어 × 2 한계에 도달했으면 쿼리 응답 시간 단축 우선(쿼리 실행 시간 절반 → TPS 2배), ② DB 서버 코어 여력이 있으면 맥스 풀 사이즈 확장 검토, ③ 위 두 방법으로 목표 TPS 미달 시 DB 자원 증설(코어 추가, 레플리카 활용).

### 단일 WAS 시나리오 예시

환경: DB 8코어, SSD, 충분한 RAM, 단일 WAS. P95 쿼리 시간 50ms, 목표 TPS 300.

- 시작 풀 사이즈: 8 × 2 + 0 = **16**
- 이론 상한 TPS: 16 ÷ 0.05 = 320; 실효 TPS(80%): **256** → 목표 300 미달
- 단계적 접근: 쿼리·인덱스 최적화 → 풀 사이즈 18~20으로 점진 확장 → 그래도 미달 시 DB 자원 증설

### 다중 WAS 환경에서의 분배

흔한 실수: WAS별로 독립적으로 풀 사이즈 16 지정 → WAS 4대 × 16 = 총 64개 → DB 허용치 초과.

올바른 접근:
```
각 WAS 풀 사이즈 = (DB 코어 × 2) ÷ WAS 인스턴스 수
```
예: 8코어 DB, WAS 4대 → 각 WAS = 16 ÷ 4 = **4개**.

| 우선순위 | WAS별 풀 사이즈 | 총 커넥션 | 특징 |
|---|---|---|---|
| DB 보호 우선 | 4 | 16 | 보수적, WAS 1대 장애 시 나머지 부담 증가 |
| 가용성 우선 | 5~6 | 20~24 | WAS 1대 장애를 견딜 여유 확보 |

오토스케일링 환경처럼 WAS 수가 동적으로 변할 때는 PgBouncer 같은 외부 풀러 사용을 권장한다.

### DB 맥스 커넥션 제약

PostgreSQL 기본 맥스 커넥션은 **100** (실사용 가능 ~90). 필수 조건: **전체 WAS 풀 합산 ≤ DB 맥스 커넥션 × 0.8** (안전 마진). AWS RDS 가이드 예시: 맥스 500이면 풀러는 400으로 설정.

장애 시나리오: WAS 5대 × 맥스 풀 30 = 150 > DB 맥스 100 → 초과 시 고정 풀은 앱 시작 즉시 오류(파드 기동 실패), 동적 풀은 트래픽 폭증 시 100개 초과 지점에서 장애 발생.

PostgreSQL은 [[프로세스]] 기반이라 커넥션당 수 MB~수십 MB 메모리를 소비하고 [[컨텍스트-스위칭]]이 누적되므로, 맥스 커넥션을 단순히 올리는 것보다 **PgBouncer 같은 중간 풀러 도입**이 권장 대안이다.

### 기존 시스템 적용 시 주의사항

"잘 동작하는 시스템은 건들지 말라" — 적용 전 반드시 피크 시간대 HikariCP 메트릭으로 평균 활성 커넥션을 측정한다.

| 활성 커넥션 / 맥스 풀 사이즈 | 판단 |
|---|---|
| < 25% | 풀 축소 안전 |
| 25~65% | 신중하게 적용 |
| 65% 이상 | 풀 사이즈 줄이지 말 것 |

이 가이드 적용처: ① 트러블슈팅 진단 기준, ② 신규 시스템 구축 시 초기값.

### 실무 함정 4가지

**① 롱 트랜잭션**: 트랜잭션 안에서 외부 API 호출·무거운 계산 → 커넥션 점유 시간 증가 → 공식에 맞는 풀도 고갈 가능. 가장 흔한 풀 고갈 원인. 처방: 트랜잭션 최대한 짧게, 외부 호출은 트랜잭션 밖으로 이동.

**② 유효 커넥션 타임아웃 미스매치**: HikariCP `maxLifetime`(기본 30분)이 DB idle timeout보다 길면 DB가 먼저 끊은 커넥션을 풀이 모르고 재사용 시도 → 오류 발생. PgBouncer `server_idle_timeout` 기본값 **10분** vs HikariCP `maxLifetime` 30분은 즉시 미스매치. RDS Proxy, NLB 개입 시도 동일. 처방: `maxLifetime`을 DB 또는 중간 계층의 idle timeout보다 **30초 이상 짧게** 설정.

**③ Cm > 1인 코드**: 중첩 트랜잭션 패턴으로 한 [[쓰레드]]가 커넥션 여러 개를 동시 점유. 처방: 풀 크기 확장보다 코드 구조 수정 우선.

**④ 커넥션 누수**: HikariCP `leakDetectionThreshold`(예: 60000 = 60초) 설정으로 풀에서 나간 커넥션이 60초 이상 반환되지 않으면 로그 경고. 핵심: 풀 크기를 키우면 해결되겠지는 섣부른 처방이며, 대부분 고갈은 커넥션 점유 시간 문제.

### 핵심 요약과 즉시 점검 체크리스트

5가지 핵심:
1. 커넥션 수가 많다고 좋지 않다 — 일정 수 초과 시 [[컨텍스트-스위칭]]·락 경쟁·캐시 교체로 처리량 감소
2. 물리 코어 × 2 (+스핀들) — 풀 사이즈 시작점; 부하 테스트로 스위트스팟 탐색
3. [[리틀의-법칙]]으로 검증 — 쿼리 실행 시간 단축을 TPS 증가의 첫 번째 수단으로
4. 작게 시작해서 측정하며 늘리기 — 임의의 큰 값으로 시작 금지
5. 롱 트랜잭션이 진짜 적 — 유발 요인 모두 제거

즉시 점검 체크리스트 8가지:
1. 맥스 풀 사이즈가 DB 물리 코어 × 2 기준인지 확인 (50·100 등 임의 큰 값 여부)
2. 고정 풀 운영: HikariCP `minimumIdle` = `maximumPoolSize` (런타임 풀 변동 오버헤드 제거)
3. 커넥션 타임아웃 기본값 유지 (너무 길면 역효과)
4. `leakDetectionThreshold` 설정으로 커넥션 누수 로그 모니터링
5. 롱 트랜잭션 제거 (불필요하게 긴 로직은 트랜잭션 밖으로)
6. HikariCP 메트릭(active·pending·idle) 대시보드 구축
7. WAS 인스턴스 수 × 맥스 풀 합산 ≤ DB 맥스 커넥션 확인; 초과 시 PgBouncer 도입 검토
8. 부하 테스트로 새츄레이션 포인트(처리량이 꺾이는 지점) 파악
