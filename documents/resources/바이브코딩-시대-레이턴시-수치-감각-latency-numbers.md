# 프로그래머가 알아야 할 레이턴시 수치 감각 (Latency Numbers)

## 요약

피터 노빅·제프 딘·콜린 스콧이 발전시킨 컴퓨팅 레이턴시 수치표를 중심으로, AI 코드 생성 시대에도 개발자가 갖춰야 할 [[레이턴시-수치-감각]]의 실무 의사 결정 가치를 설명하는 영상이다. 바이브코딩 시대일수록 수치 외우기보다 차수 감각이 진짜 경쟁력이라는 것이 핵심 주장이다.

## 핵심 내용

### 코더와 아키텍트를 가르는 기준

영상은 DB 응답 지연에 Redis 캐시 도입을 제안한 주니어 개발자가 시니어의 "얼마나 느린데, 캐시로 얼마나 빨라지냐"는 질문에 답하지 못한 시나리오로 시작한다. 이 장면은 코더와 아키텍트의 차이를 압축한다 — 코드를 잘 쓰는가가 아니라 **근거 있는 의사 결정**을 할 수 있는가. AI가 이미 코드 작성을 담당하는 시대에, 아키텍트에게 필요한 것은 근거·기준·의사 결정 능력이다.

### Latency Numbers Every Programmer Should Know 개요

CPU·메모리·디스크·네트워크의 시간 비용을 정량화한 이 수치표는 백엔드·시스템 설계 분야의 전 세계적 레퍼런스다. DDIA(백엔드 바이블), 알렉시의 시스템 디자인 면접 책(100만 부 이상 판매), ACM Queue, 구글 리서치·코넬대 자료에서 인용된다. 이 표가 답해 주는 질문들: 캐시를 도입할 가치가 있는가, 네트워크 호출 횟수를 줄이면 얼마나 빨라지는가, 데이터를 메모리에 두는 것이 정말 큰 차이인가, 리전을 분리하면 응답이 얼마나 느려지는가, SSD가 RAM의 대안이 될 수 있는가.

차수 감각의 개념과 실무 의사 결정 근거로서의 위상 상세는 [[레이턴시-수치-감각]] 참조.

### 수치의 역사: 세 인물

**피터 노빅(2001)**: 구글 리서치 디렉터, AI 교과서 《Artificial Intelligence: A Modern Approach》 공저자. "Teach Yourself Programming in Ten Years" 에세이에 11가지 레이턴시 수치표를 최초 포함했다. 2001년 기준 주요 수치: CPU 명령 1 ns, L1 캐시 0.5 ns, L2 캐시 7 ns, 메인 메모리 100 ns, 1 Gbps로 1 KB 전송 20 μs, HDD 탐색 8 ms, 메모리에서 1 MB 순차 읽기 250 μs, 미국→유럽 패킷 왕복 150 ms. 단일 PC 기준 로컬 하드웨어의 물리적 제약을 정량화한 관점으로, 그의 진짜 강조점은 정확한 수치 암기가 아니라 CPU(ns) vs 메모리(100 ns) vs 디스크(ms) vs 네트워크(ms) 간 **차수의 감각**이었다.

**제프 딘(2009)**: MapReduce·BigTable·TensorFlow 공동 설계자. LADIS(대규모 분산 시스템 학회) 키노트에서 노빅의 표를 구글 분산 시스템 경험 기반으로 확장했다. 추가된 항목: 1 KB Gzip 압축 3 μs, SSD 랜덤·순차 읽기, 데이터센터 내부 RTT 500 μs. 압축 트레이드오프 사례: 네트워크 직접 전송 10 μs vs 압축(3 μs) 후 전송(5 μs) = 8 μs → 압축이 2 μs 이득. "중요한 것은 실제로 만들지 않고도 시스템의 성능을 추정할 수 있는 능력이다." 조나스 보너(Jonas Bonér)가 2012년 딘의 강연을 GitHub Gist로 정리해 SSD 항목 2개를 추가한 버전이 현재 업계 표준으로 인용된다.

**콜린 스콧(2012~)**: UC Berkeley 출신. 하드웨어는 시간에 따라 빠르게 진화하므로 수치를 시간의 함수로 모델링하고, 연도 슬라이더로 레이턴시를 자동 계산하는 인터랙티브 웹페이지를 제작했다. 진짜 가치: 연도가 바뀌어도 CPU 캐시 → 메모리 → SSD → HDD → 네트워크라는 레이턴시 서열과 격차는 변하지 않음을 시각적으로 체감할 수 있다. 한계: 메모리·네트워크처럼 개선 속도가 제한적인 영역에서는 실제 수치와 차이 날 수 있으므로 정확한 수치가 필요하면 최신 벤치마크를 참조해야 한다.

### 실무 활용: 의사 결정 사례 3가지

**캐시 도입 의사 결정**: HDD 기반 레거시 DB 조회가 느려 Redis 캐시 도입을 검토할 때 — HDD 탐색 ~10 ms, 데이터센터 내부 RTT 500 μs, Redis 메모리 조회 수십 ns. HDD 대비 Redis가 차수 자체가 다를 정도로 빠르므로 도입 가치가 있다. 단, SSD 기반 DB라면 성능 차이가 줄어들어 부하 분산 관점으로 재검토해야 한다.

**마이크로서비스 분리의 진짜 비용**: 특정 기능을 별도 MSA로 분리할지 결정할 때 — 로컬 메모리 내 함수 호출 수 ns vs 데이터센터 내부 네트워크 호출 500 μs, 차이 **10만 배 이상**(직렬화·역직렬화 비용 추가). 호출 빈도가 높다면 신중하게 접근해야 하며, 무조건 분리가 답은 아니다. MSA는 레이턴시 외에 확장성·독립성 등 아키텍처 관점도 함께 고려해야 한다.

**시스템 디자인 면접(100만 QPS)**: "URL 단축 서비스를 100만 QPS로 처리하려면?"에 대한 수치 기반 추론 — 메모리 조회 100 ns → 이론상 단일 서버 초당 1,000만 건 처리 가능이므로 메모리에서 끝나는 작업이면 한 대로 충분, 디스크 DB 조회 수 ms → 단일 서버로 100만 QPS 불가, 네트워크 호출 500 μs → 서비스 간 호출 횟수를 줄이지 않으면 병목. 이 감각으로 캐시 필수·[[샤딩]] 필요·호출 최소화 이유를 숫자로 정량화해 설명할 수 있다.

### 수치 활용 시 주의점 4가지

1. **정확한 수치를 외우려 하지 마라** — 실제 환경과 정확히 일치하지 않는 근사값이다. 핵심은 ns·μs·ms 단위 차이의 감각이다.
2. **전부 외우지 않아도 된다** — L1 캐시, 메인 메모리, SSD, 데이터센터 내부 RTT, HDD, 대륙 간 패킷 전송 정도만 알아도 의사 결정이 가능하다.
3. **절대값이 아닌 상대적 격차(배수)가 중요하다** — 연도마다 절댓값은 변하지만 "RAM이 SSD보다 약 200배 빠르다" 같은 비율 감각은 유지된다.
4. **레이턴시만이 전부가 아니다** — 실무에서는 처리량(Throughput)도 함께 고려해야 하며, 배치·병렬 처리로 레이턴시 비용을 상쇄할 수 있는 환경도 있다.

### 결론: 바이브코딩 시대의 본질

구조 설계·하중 계산을 모르는 건축가, 재료와 불의 성질을 모르는 요리사, 악보도 못 읽는 작곡가는 없다. 개발 본질에 관심 없이 AI에만 의존해 쏟아낸 코드는 결국 저품질 시스템이 된다. [[레이턴시-수치-감각]]이 대표하는 아키텍처적 감각이 바이브코딩 시대의 진짜 경쟁력이다.
