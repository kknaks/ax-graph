## 키-밸류 데이터베이스

- 데이터를 **키-밸류 형태**로 저장하는 가장 단순한 DB 유형
- 단독 메인 DB로는 실용성이 낮고, **서브 용도**로 주로 사용

### Redis (레디스)
- 키-밸류 형태이지만 데이터를 **하드디스크가 아닌 RAM에 저장** → 수십~수백 배 빠른 속도
- 활용 방식: 메인 DB를 따로 두고, 자주 쓰이는 데이터를 Redis에 복사해 캐시처럼 제공
- 주요 용도: **캐싱**, **pub/sub 구현** 등 서브 DB 역할
- 최근 Redis 단독으로 모든 기능을 커버하는 업그레이드 버전도 출시됐으나, 실사용은 드문 편

## 관계형 데이터베이스 (RDBMS)

- 데이터를 **테이블(표) 형태**로 저장 — 엑셀과 유사한 구조
- 대표 DBMS: **Oracle, MySQL, PostgreSQL**
- 데이터 저장·조회에 **SQL** 문법 사용 (비교적 쉬운 편)
- 데이터베이스 점유율 상위권 대부분이 관계형 DB

### 정규화
- 관계형 DB의 핵심 개념: **데이터 중복을 제거**하기 위해 중복 데이터를 별도 테이블로 분리
- 단점: 입출력 쿼리가 복잡해지는 경향

### 트랜잭션
- 기본적으로 **트랜잭션 기능** 내장 → 금융 거래 등 중요한 기능을 안전하게 구현 가능

### 적합한 상황
- **데이터 정확도**가 입출력 속도보다 중요한 경우
- 일반적인 서비스에서 범용적으로 사용

> 참고: '관계형'이라는 명칭은 데이터 간 관계를 잘 표현해서가 아니라, 수학 용어 **'릴레이션(Relation, 행렬 개념)'** 에서 유래한 것

## 그래프 데이터베이스

- **노드(Node)** 를 만들고, 노드 간의 **관계(엣지)와 방향**을 함께 저장
- 대표 DBMS: **Neo4j**
- 데이터 조회 언어: **Gremlin(그레믈린) / Cypher** 계열의 그래프 쿼리 언어

### 적합한 상황
- 자료 간의 관계·방향을 중점적으로 저장해야 할 때
- 예시: 비행기 노선, SNS 친구 관계, 감염 경로 추적, **추천 서비스**

---

## 도큐먼트 데이터베이스

- 대표 DBMS: **MongoDB, CouchDB, Firestore**
- 구조: **컬렉션(폴더)** 안에 **도큐먼트(파일)** 를 두고, 각 도큐먼트에 **JSON 형태**로 데이터 저장

### 특징
- 스키마 미리 정의 불필요 — 필드를 자유롭게 추가해도 에러 없음 (유연한 구조)
- **정규화를 하지 않음** → 데이터 중복 허용, 입출력 문법이 단순
- **분산 처리**를 염두에 두고 설계된 DB → 수평 확장이 쉬움

### 단점
- 분산 환경에서 DB 간 **데이터 정확도(일관성)** 가 떨어질 수 있음

### 적합한 상황
- 정확도보다 **대량 입출력**이 중요한 서비스

---

## 컬럼 패밀리 데이터베이스

- 대표 DBMS: **Apache Cassandra, Google Bigtable**
- 구조: 테이블·로(Row)를 만들고, 로마다 **자유롭게 컬럼을 추가**해 데이터 기입 → 표 형식이지만 유연
- SQL이 아닌 **자체 쿼리 언어** 사용 (예: Cassandra의 **CQL**)
- 정규화 없음 → 입출력 문법 단순
- **분산 처리 성능 우수**

### 적합한 상황
- 관계형 DB처럼 표 형식으로 저장하되 유연성이 필요한 경우
- 대규모 입출력을 감당해야 하는 서비스

## 시계열 데이터베이스

- **시간 기록(타임스탬프)** 기반 데이터를 쉽게 저장·분석하는 데 특화
- 시계열 데이터 저장 및 분석 용도로 사용

---

## 검색 엔진 (Search Index DB)

- 대표 서비스: **Elasticsearch, Amazon CloudSearch**
- 일반 DB로도 사용 가능하나, 실제로는 **검색 인덱스 보관 전용**으로 주로 사용
- 동작 방식: 기존 DB에서 데이터를 가져와 **인덱스(색인)** 를 생성·보관 → 검색 요청 시 인덱스 기반으로 빠른 결과 제공
- 부가 기능: **실시간 검색어 추천**, **자동완성**, **오타 교정**

### 적합한 상황
- 검색 기능이 중요한 서비스

---

## 최종 요약 — DB 선택 기준

- **일반적인 경우**: 관계형 DB 또는 도큐먼트 DB 중 하나 선택
  - **데이터 정확도**가 중요 → **관계형 DB** (MySQL, PostgreSQL 등)
  - **대량 입출력**이 중요하고 정확도 우선순위가 낮음 → **도큐먼트 DB** (MongoDB 등)
- **캐싱·속도** 최우선 서브 DB → **Redis**
- **관계·방향** 데이터 중심 → **그래프 DB** (Neo4j)
- **표 형식 + 대규모 분산** → **컬럼 패밀리 DB** (Cassandra)
- **검색 기능** 특화 → **Elasticsearch**
