## 1. 제안 배경

현재 고객사 데이터는 **네트워크 공유폴더**에 집중되어 있으며, 별도의 NAS나 문서관리시스템 없이 일반 데스크탑을 사실상 파일 서버로 사용 중이다.

| 구분 | 현재 문제 | 경영 리스크 |
|---|---|---|
| 데이터 위치 | 파일 위치를 담당자 기억에 의존 | 담당자 변경/퇴사 시 업무 단절 |
| 최신성 | 최신 파일과 과거 파일 구분 어려움 | 잘못된 자료 기반 의사결정 |
| 권한 | 폴더 권한 중심의 느슨한 통제 | 민감 데이터 노출 위험 |
| 검색 | 파일명/폴더명 기반 수동 검색 | 업무 시간 낭비 |
| 보존 | 오래된 데이터가 계속 혼재 | 저장 비용 증가, 정리 불가 |
| AI 활용 | 문서 위치/권한/맥락이 정리되지 않음 | Graph RAG, AI 검색 도입 어려움 |

> 회사 데이터를 "어디에 있고, 누가 접근 가능하며, 언제 보관/폐기되어야 하고, 어떻게 검색/활용할 수 있는지" 관리 가능한 자산으로 전환하는 DX 운영 체계 구축이다.

## 2. 전체 방향성

- **기존 데이터**: 즉시 이전하지 않고 먼저 **메타데이터화**한다.
- **신규 데이터**: 새로운 표준 저장 위치에 수집하고, 생성 시점부터 메타데이터와 권한 정책을 연결한다.

처리 흐름 요약:
1. 기존 공유폴더 전체 스캔 → 메타데이터 카탈로그 생성
2. 고객사/프로젝트/부서/기간 기준 분류 → 권한 정책 연결 → 검색 및 Graph RAG 활용
3. 신규 데이터는 표준 저장 위치 저장 시 자동 메타데이터 등록 → 카탈로그 편입
4. 아카이브 정책을 통해 장기 보관 저장소로 전환

## 3. Before / After

### 현재 운영 방식의 문제 흐름
- 사용자가 공유폴더에 직접 접근 → 폴더/파일명으로 수동 검색
- 파일 위치를 모를 경우 담당자에게 문의 → 담당자도 기억 못하면 **재작성/중복 저장/누락** 발생
- 결과: 업무 단절, 중복 데이터, 최신본 혼선, 권한 불명확

### 개선 후 운영 방식
- 사용자가 **검색/관리 포털** 접근 → 사용자 인증 → 역할/부서/그룹 확인
- **메타데이터 기반 검색** → RBAC 접근 권한 판단
- 허용된 경우: 문서 위치/요약/관련 데이터 제공, 업무 활용(조회/다운로드/AI 질의응답)
- 차단된 경우: 검색 결과에서 제외

## 4. 목표 운영 모델

데이터 운영 흐름: **생성 → 표준 위치 저장 → 자동 메타데이터 등록 → 고객사/프로젝트/부서 매핑 → 접근권한 적용 → 검색 및 활용 → 보존 기간 경과 시 아카이브 전환**

**메타데이터는 아카이브 전환 후에도 유지하고, 원본만 장기 보관소로 이동한다.**

운영 5대 원칙:

| 원칙 | 설명 |
|---|---|
| 원본 위치 추적 | 레거시 파일은 이동 전에도 현재 위치를 정확히 기록 |
| 자동 수집 | 신규 파일은 저장 시점부터 자동 등록 |
| 권한 우선 | 검색과 AI 활용 모두 RBAC 기준으로 제한 |
| 최신/장기 분리 | 최근 데이터와 장기 보관 데이터를 분리 운영 |
| 메타데이터 중심 | 오래된 데이터는 원본보다 메타데이터를 중심으로 찾고 관리 |

## 5. 레거시 데이터 운영 플로우

기존 공유폴더는 즉시 폐기하거나 전면 이전하지 않는다.

처리 단계:
1. 기존 공유폴더 전체 스캔 → 파일 목록 생성 → 기본 메타데이터 추출
2. 고객사/프로젝트/부서 기준 분류
3. 활용 상태 판단:
   - 최근 사용 → **활성 데이터** → 검색 대상 등록
   - 낮은 사용 빈도 → **보관 후보** → 아카이브 정책 적용
   - 중복/불명확 → **정리 검토 대상** → 현업 확인
4. 모든 경로 → 권한 기반 조회로 합류

> 기존 데이터를 당장 모두 옮기는 것이 아니라, 먼저 "찾을 수 있고 통제 가능한 상태"로 만든 뒤 중요도와 사용 빈도에 따라 단계적으로 이전/보관한다.

## 6. 신규 데이터 운영 플로우

사용자는 정해진 위치에 저장하면 시스템이 자동으로 관리하도록 설계한다.

시퀀스:
1. 사용자가 파일 저장
2. 파일 감시/등록 에이전트가 생성 이벤트 감지
3. 메타데이터 카탈로그에 파일 위치/속성 등록
4. 권한/보존 정책 서비스에서 접근권한·보존기간·민감도 반환
5. 검색 인덱스 갱신
6. 사용자가 권한 내 검색/질의응답 활용

---

## 7. 실시간 트래킹 운영 구조

**이벤트 기반 감시** + **주기적 전체 스캔** 병행:
- 이벤트 감시: 생성/수정/삭제/이동 이벤트를 빠르게 반영
- 주기적 스캔: 누락 확인, 권한 변경 확인, 중복 확인(보정 역할)
- 두 경로 모두 **변경 이벤트 큐** → 메타데이터 갱신 → 변경 이력 저장 + 검색 인덱스 갱신 + 운영 대시보드 반영

## 8. 데이터 라이프사이클 정책

사용 빈도와 보존 필요성에 따라 **Hot / Warm / Cold** 3단계로 분리한다.

| 구분 | 대상 | 운영 방식 |
|---|---|---|
| Hot | 최근 1년, 진행 중 업무 | 빠른 접근, 클라우드/협업 저장소 중심 |
| Warm | 1~3년, 참조 가능성 있음 | 검색 가능, 접근 빈도 낮음 |
| Cold | 3년 이상, 장기 보존 | 원본은 아카이브, 메타데이터 중심 조회 |

Cold 단계 이후 보존 만료 검토 시 법적/계약상 보존 필요 여부에 따라 Cold 유지 또는 **폐기 승인 프로세스** 진행.

### PARA 적용 방식

13개 내외 부서가 함께 사용하는 환경에서 PARA만으로 전체 분류 체계를 구성하기에는 단순하다. **PARA는 폴더 구조의 최상위 기준이 아니라, 데이터의 "운영 상태와 활용 목적"을 표현하는 메타데이터 축**으로 보조 적용한다.

6축 다차원 메타데이터 모델:

| 분류 축 | 의미 | 예시 |
|---|---|---|
| 책임 부서 | 데이터의 관리 책임 주체 | 영업, 재무, 인사, 운영, 품질 |
| 업무 맥락 | 데이터가 속한 고객사/프로젝트 | A고객사, 2026 유지보수 프로젝트 |
| 문서 유형 | 업무상 문서의 성격 | 계약서, 제안서, 견적서, 보고서, 도면 |
| PARA 상태 | 데이터의 활용 목적과 상태 | Projects, Areas, Resources, Archives |
| 권한/보안 | 누가 볼 수 있는지에 대한 기준 | 부서 권한, 프로젝트 참여자, 임원 권한 |
| 보존 정책 | 언제까지 Hot/Warm/Cold로 운영할지 | 최근 1년, 3년 보관, 7년 보존 |

PARA 보조 분류 내용:
- **Projects**: 진행 중 프로젝트, 고객사별 산출물, 계약/제안/보고 자료
- **Areas**: 상시 운영 업무, 영업/회계/품질/CS, 부서별 기준 문서
- **Resources**: 참고자료, 템플릿, 매뉴얼
- **Archives**: 완료 프로젝트, 과거 고객사 데이터, 장기 보존 자료

메타데이터 예시:

```yaml
file_path: "\\\\share\\sales\\client-a\\2026\\contract.pdf"
department: "영업"
owner_team: "영업1팀"
para_type: "Projects"
client: "Client A"
project: "2026 유지보수 계약"
document_type: "계약서"
sensitivity: "Confidential"
storage_tier: "Hot"
retention_period: "7년"
access_groups:
  - sales
  - legal
```

## 9. 접근권한 및 Graph RAG 운영

AI 검색과 **Graph RAG**는 반드시 **권한 정책 위에서** 동작해야 한다.

핵심 원칙: **사용자가 접근할 수 없는 파일은 검색 결과, 요약, AI 답변의 근거 문서에 포함되지 않아야 하며, 문서 존재 여부도 노출하지 않는다.**

처리 흐름:
1. 사용자 질문 → 사용자 인증
2. 역할/부서/그룹 확인 → 접근 가능한 문서 범위 계산
3. RBAC 조건으로 메타데이터 필터링 → 허용 문서만 검색
4. Graph/Vector 검색 → AI 답변 생성 → 출처 제공
5. 권한 없는 문서는 제외되고 존재 여부도 노출되지 않음

권한 정책 기본 단위:

| 대상 | 기준 |
|---|---|
| 사용자 | 부서, 직무, 역할, 프로젝트 참여 여부 |
| 문서 | 고객사, 프로젝트, 민감도, 소유 부서 |
| 정책 | 허용 그룹, 차단 조건, 보존 기간, 감사 필요 여부 |

## 12. 경영진 의사결정 포인트

경영진이 결정해야 할 4가지 항목:

| 의사결정 항목 | 선택지 |
|---|---|
| 우선순위 | 리스크 통제 / 검색 효율 / AI 활용 기반 |
| 저장소 방향 | 협업 저장소(Google Drive/SharePoint/OneDrive) / 오브젝트 스토리지(GCS/S3/Azure Blob) / NAS 병행 |
| 운영 책임 | IT 단독 / 현업+IT 공동 / 데이터 관리자 지정 |
| 적용 범위 | 특정 부서 파일럿 / 고객사 데이터 전체 / 전사 확대 |

우선 목표별 초기 접근:
- **리스크 통제** → 레거시 데이터 목록화/권한 정비 우선
- **업무 효율** → 검색/포털/신규 저장 정책 우선
- **AI 활용** → 메타데이터 + RBAC + Graph RAG 기반 우선

모든 경로 공통: 1차 예산(진단/카탈로그/감시) → 저장소 전략 결정

## 13. 기대 효과

효과 매트릭스 (업무효율 × 통제수준 기준):
- 현재 공유폴더 운영: 낮은 효율 + 낮은 통제 (위험 구간)
- 단순 클라우드 이전: 효율 향상, 통제 미흡
- 메타데이터 카탈로그 구축: 통제 강화, 효율 중간
- **RBAC 기반 Graph RAG 운영**: 높은 효율 + 높은 통제 (전략 자산화)

| 영역 | 기대 효과 |
|---|---|
| 업무 연속성 | 담당자 기억에 의존하지 않고 데이터 위치 추적 가능 |
| 보안 | 권한 기반 검색과 접근 통제로 민감 데이터 노출 감소 |
| 생산성 | 고객사/프로젝트 단위 검색 시간 단축 |
| 비용 | 장기 데이터 아카이브로 저장소 비용과 혼재 문제 완화 |
| AI 활용 | Graph RAG, 문서 요약, 지식 검색 기반 확보 |
| 경영 관리 | 데이터 현황, 증가량, 보존 상태를 대시보드로 관리 |

## 14. 핵심 메시지

본 프로젝트는 **저장소 교체 사업이 아니다.**

전환 단계: 파일 저장 중심 → 데이터 위치 추적 → 메타데이터 관리 → 권한 기반 검색 → 아카이브 운영 → **AI 활용 가능한 데이터 자산**
